## Задание 2. «Создание заказа» — проверка API и обработки ошибок
### Контекст
Интернет-магазин предоставляет API для **создания заказа**. Клиент отправляет HTTP-запрос на **POST /orders**.
**Пример запроса**:
`{
	"user_id": 15,
	"items": [
		{
		"product_id": 101,
		"quantity": 2
		}
	]
}`
> **Требование 1.** Для **создания заказа** необходимо передать `user_id` и непустой список `items`.
>
> **Требование 2.** Каждый товар должен содержать `product_id` и `quantity`.
>
> **Требование 3.** Количество товара `(quantity)` должно быть **положительным целым числом**.
>
> **Требование 4.** Если **все данные корректны** и **товары доступны в нужном количестве**, система создаёт заказ и возвращает *HTTP 201 Created*, идентификатор заказа и его статус `created`.
>
> **Требование 5.** Если запрос **содержит некорректные данные**, система возвращает *HTTP 400 Bad Request*.
>
> **Требование 6.** Если **товар не существует**, система возвращает *HTTP 404 Not Found*.
>
> **Требование 7.** Если **товара недостаточно на складе**, система возвращает *HTTP 409 Conflict*.
>
> **Требование 8.** Если **сервис проверки остатков временно недоступен**, система возвращает *HTTP 503 Service Unavailable*.

Система должна их сложить и создать один элемент, выдавать ошибку, или позиции будут созданы отдельно?

   **Вопрос** - какую ошибку пользователь должен получить при одновременных ошибках `400`, `404` и `409`? Вместе с ошибкой приходит ли массив с данными, вызвавшими ошибку?

  ```json
	"message": "Field 'quantity' must be a positive integer, got -1"
  }
  ```
  Заказ в БД не создается, остатки на складе не изменяются.
  Для Тест-кейса 2 использована комбинация классов эквивалентности и граничных значений `>= 1` значение `-1` выбрано как критическая граница для проверки строгой валидации вложенных полей и предотвращения логических ошибок инвентаря.

**Тест-кейс 3: Обработка сбоя зависимого сервиса проверки остатков**
Предусловия:
- в системе существует пользователь `user_id` = 15;
- в системе существует товар `product_id` = 101;
- в тестовом окружении сымитирована недоступность сервиса складского учета.

HTTP Метод и Endpoint:
- `POST /orders`

Тело запроса:
  ```json
  {
	"user_id": 15,
    "items": [
      {
        "product_id": 101,
        "quantity": 2
      }
    ]
  }
  ```
Ожидаемый HTTP-статус: 
- `503 Service Unavailable`
Ожидаемый результат:
``` json
  {
	"status": 503,
	"error": "Service Unavailable",
	"service": "warehouse-service",
	"message": "Warehouse inventory service is temporarily unreachable"
  }
```
Заказ не создается, транзакция отменяется.
Для Тест-кейса 3 применена техника тестирования устойчивости к отказам: сетевые сбои складских систем неизбежны, поэтому кейс проверяет корректную обработку внешнего таймаута, откат локальной транзакции и возврат контролируемого статуса `503` вместо аварийного падения сервера с ошибкой `500`.

#### 4. **Проверка результата**.
Объясните, почему недостаточно проверить только HTTP-статус ответа. Что ещё нужно проверить, чтобы убедиться, что заказ действительно создан корректно?

Проверка одного лишь HTTP-статуса `201 Created` является поверхностной, так как статус подтверждает лишь успешное завершение функции контроллера на бэкенде. Для гарантии целостности бизнес-транзакции необходимо проверить:
1. **Тело ответа:** проверить генерацию валидного `order_id`, корректность эхо-данных.
2. **Базу данных:**  в таблице `orders` появилась запись с новым `id` статусом created и точным временем создания `created_at`; в таблице связей `order_items` корректно записаны все переданные товары с сохранением цены на момент покупки.
3. **Списание остатков:** в сервисе склада остаток товара `product_id` уменьшился ровно на `quantity`.

#### 5. **Бонус вопрос**.
Клиент отправил запрос на создание заказа, но соединение оборвалось до получения ответа. Клиент не знает, создался заказ или нет, и отправляет тот же запрос повторно. Какие проблемы могут возникнуть? Какие вопросы вы зададите команде и что предложите проверить?

Может возникнуть проблема нарушения идемпотентности (дублирование заказа). Если первый запрос успел дойти до сервиса и создать заказ, а разрыв соединения произошел по пути обратно, то без необходимой защиты сервер воспримет повторный запрос как новый заказ, зарегистрирует и повторно спишет остатки со склада, а с пользователя могут дважды списать денежные средства. Если товара на складе хватало только на один заказ, то повторный запрос вернет ошибку `409`, чем введет пользователя в заблуждение.
У команды можно спросить:
- Реализован ли механизм ключей идемпотентности для метода `POST /orders` ?
- Какое время жизни у ключа идемпотентности в кэше/хранилище дедупликации?
- Как система реагирует на параллельные повторные запросы с одинаковым телом от одного пользователя?
Можно предложить проверить:
1. Тест повторной отправки с ключом идемпотентности:
   Отправить запрос на создание заказа, оборвать соединение, повторить запрос с тем же ключом идемпотентности. Сервер должен вернуть ответ HTTP `201 Created` с первоначальным `order_id` без создания повторных записей в БД и без вторичного списания остатков
2. Тест параллельных дублирующих запросов: 
   Отправить несколько одинаковых запросов на создание заказа одновременно. Убедиться, что технически исключено создание нескольких заказов.

### Структура таблиц

| id  | user_id | total | status    | created_at |

| 102 | 1       | 700   | cancelled | 2024-03-05 |

### Задания (напишите SQL)
#### 1. Вывести список пользователей **из Москвы**.

``` sql 
SELECT
	id,
	name,
	city
FROM users
WHERE city = 'Москва';
```
Простая фильтрация по точному совпадению значения города.
#### 2. Вывести **общую сумму оплаченных заказов** по каждому пользователю (включая пользователей без заказов).

``` sql
SELECT 
    u.id, 
    u.name, 
    COALESCE(SUM(o.total), 0) AS total_paid_sum
FROM users u
LEFT JOIN orders o ON u.id = o.user_id AND o.status = 'completed'
GROUP BY 
    u.id, 
    u.name;
```
Используется `LEFT JOIN`, чтобы не потерять пользователей, у которых нет заказов.
Условие o.status вынесено в `ON`, поскольку если поместить его в `WHERE`, то пользователи без оплаченных заказов отфильтруются.
#### 3. Вывести пользователей, у которых **есть хотя бы один заказ со статусом `returned`**.

```sql
SELECT 
    u.id, 
    u.name
FROM users u
JOIN orders o ON u.id = o.user_id
GROUP BY 
    u.id, 
    u.name
HAVING COUNT(CASE WHEN o.status = 'returned' THEN 1 END) >= 1;
```
Группируем заказы по пользователю, а с помощью `HAVING` проверяем, что количество возвращенных заказов >= 1
#### 4. Вывести **топ-3 пользователей по сумме оплаченных заказов**.

```sql
SELECT 
    u.id, 
    u.name, 
    SUM(o.total) AS total_paid
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE o.status = 'completed'
GROUP BY 
    u.id, 
    u.name
ORDER BY total_paid DESC
LIMIT 3;
```
Фильтруем оплаченные заказы, группируем по пользователям, суммируем суммы заказов, сортируем по убыванию и берем только первые 3
#### 5. Вывести пользователей, **не делавших ни одного заказа**.

```sql
SELECT 
    u.id, 
    u.name
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
GROUP BY 
    u.id, 
    u.name
HAVING COUNT(o.id) = 0;
```
`LEFT JOIN ` подтягивает заказы, группируем по каждому пользователю с помощью `HAVING` отсекаем тех, у кого количество связанных заказов равно нулю.
#### 6. *(дополнительно, на оценку)* Написать запрос, который выводит для каждого города **среднюю сумму одного заказа** по оплаченным заказам.

```sql
SELECT 
    u.city, 
    AVG(o.total) AS avg_order_amount
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE o.status = 'completed'
GROUP BY u.city;
```
`WHERE` отбирает исключительно оплаченные заказы, `GROUP BY u.city` собирает данные по городам, `AVG` вычисляет среднюю сумму заказа в каждом городе.
